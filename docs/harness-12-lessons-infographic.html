Harness Atlas · 12 Lessons

Harness Engineering for Real Agents

这不是一张普通课程目录，而是一张从 单个 agent loop 进化到 真实工程协作 runtime 的能力地图。12 节课的重点不是“会调 LLM”，而是 “会搭建一个能执行、能恢复、能协作、能隔离的 agent harness”。

12 节课，从最小闭环到多 agent + worktree 隔离执行。

S01 Foundation

The Agent Loop

让模型第一次真正接入“外部世界”。

解决的问题：没有循环，模型就无法持续观察、行动、再观察。
messagestool_result 回灌最小闭环

新增机制：基于 `stop_reason == tool_use` 的循环，让模型可以反复调用工具直到任务完成。

产出能力：agent 能用 `bash` 创建文件、看目录、读 git 状态，而不是只停留在回答层。

为什么重要：这是后面所有任务系统、子 agent、后台任务的底座。

S02 Foundation

Tool Use

新增工具时，不重写主循环。

解决的问题：如果每加一个工具都改 loop，系统会越来越脆弱。
dispatch mapschema统一入口

新增机制：`TOOL_HANDLERS` / dispatch registry，把循环和工具实现解耦。

产出能力：除了 `bash` 之外，还能扩展 `read_file`、`write_file` 等能力而不破坏主结构。

为什么重要：没有可扩展工具层，后面的 todo、task、team 都会耦死在一起。

S03 Foundation

TodoWrite

让 agent 先计划，再逐项执行。

解决的问题：没有显式计划时，agent 容易跳步、忘事、来回漂移。
外显工作记忆任务拆分状态勾选

新增机制：`TodoWrite` 作为外显工作记忆，让模型把脑内计划显性化。

产出能力：agent 会先列步骤，再逐步完成，过程更可解释，也更容易 debug。

为什么重要：从这一课开始，harness 不只是执行器，而是开始管理“工作过程”。

S04 Foundation

Subagent

把大任务拆给独立上下文处理。

解决的问题：所有问题塞进一个长对话，会造成上下文污染。
上下文隔离子任务回传职责切分

新增机制：主 agent 通过 `spawn_subagent` 把子问题交给独立 `messages[]` 处理。

产出能力：复杂问题可以局部求解，再把精简结果带回主线。

为什么重要：这是多 agent 和 worktree 隔离前，最早的“隔离思维”。

S05 Runtime

Skill Loading

按需加载知识，而不是把一切塞进 prompt。

解决的问题：system prompt 越来越长，模型会失焦、成本也会上升。
skills/按需注入知识模块化

新增机制：运行时发现并加载 skill 文件，只在需要时把知识交给模型。

产出能力：agent 不必预装所有知识，而是像工程系统一样按模块组装能力。

为什么重要：这让 harness 开始具备“上下文预算管理”的意识。

S06 Runtime

Context Compact

上下文终会爆满，必须主动压缩。

解决的问题：长对话会拖慢性能、推高成本，还会让模型遗忘关键事实。
摘要层保留层丢弃层

新增机制：对对话进行分层：该保留什么、该摘要什么、该丢弃什么。

产出能力：即使任务跑得很久，agent 依然能记住目标、约束、已完成事项。

为什么重要：没有 compact，后面真正长期运行的任务系统会越来越不稳定。

S07 Runtime

Task System

把目标、依赖、状态持久化到磁盘。

解决的问题：单次对话结束后，任务状态就会消失。
.tasks/状态流转JSON 持久化

新增机制：任务实体、依赖关系、状态机和文件化持久层。

产出能力：关闭进程再启动，agent 仍知道“哪些任务还没做完”。

为什么重要：从这一步开始，harness 已经是 runtime，而不是一次性脚本。

S08 Runtime

Background Tasks

让慢命令去后台，前台 agent 不被阻塞。

解决的问题：长时间 shell 命令会卡死整个流程。
后台任务轮询回收并行思考

新增机制：启动后台任务、保存 job 状态、在结果就绪后再回收。

产出能力：agent 可以一边触发慢任务，一边继续处理别的工作。

为什么重要：真正的工程 runtime 不能被一个长命令锁死。

S09 Team

Agent Teams

一个 agent 不够时，组织成团队。

解决的问题：复杂任务单 agent 效率低，上下文也会拥堵。
角色分工inbox/outbox并行推进

新增机制：成员身份、异步邮箱通信、队友持久化状态。

产出能力：多个 agent 能并行认领不同任务，不再只有一个大脑单线程工作。

为什么重要：这是从“agent”跨到“team runtime”的门槛。

S10 Team

Team Protocols

团队不是靠喊话，而是靠协议治理。

解决的问题：没有统一消息结构时，多 agent 很快会混乱。
request/response结构化字段可追踪通信

新增机制：协议化的请求、回复、确认格式，让协作从“聊天”变成“操作系统接口”。

产出能力：消息可以追踪、校验、重放，也更适合未来扩展审计与自动化。

为什么重要：没有协议，团队越大越乱；有协议，协作才可能稳定。

S11 Team

Autonomous Agents

队友自己找活干，而不是等领导逐个指派。

解决的问题：所有调度都靠中心节点，会形成瓶颈。
自主认领任务池扫描自组织

新增机制：周期性扫描任务池，根据依赖和角色自主 claim 工作。

产出能力：多个 agent 可以像一个轻量型工程团队那样自组织运转。

为什么重要：这一步让系统从“中心派单”走向“自治协作”。

S12 Team

Worktree Isolation

任务系统管理目标，worktree 管理文件隔离。

解决的问题：多 agent 并行改代码时，文件改动会互相污染。
.worktrees/任务绑定目录并行开发

新增机制：每个 task 绑定独立 worktree / workspace，在文件系统层面隔离任务。

产出能力：多个任务可以并行修改代码，彼此互不踩踏，后续再进入 review / merge 流程。

为什么重要：这是从“能协作”走向“能真实写代码交付”的关键一步。

毕业项目映射

学完 12 节课之后，最终不是得到一个更会聊天的 bot，而是得到一个真正能组织工程工作的本地 runtime。这也是 `RepoPilot Harness` 的价值所在。

最终汇聚成什么？

这 12 节课组合起来，构成了一条非常清晰的工程化主线： `loop` 负责让 agent 动起来，`tools` 负责触达外部世界，`todo` 和 `task system` 负责让工作过程可见、可恢复，`background jobs` 负责不阻塞，`teams + protocols + autonomy` 负责协作治理，`worktree isolation` 负责把真实代码执行纳入 runtime 边界内。

运行时层

loop、tool dispatch、context compact、background jobs

工作流层

todo、task system、持久化状态、恢复能力

协作层

subagent、teams、protocols、autonomous claiming

执行隔离层

task-worktree 绑定、并行文件修改、真实产物交付

RepoPilot Harness 对应关系

  • S01-S04：构成最小 agent execution 核心
  • S05-S08：构成长期运行的 runtime 能力
  • S09-S12：构成工程协作台的组织与隔离能力

所以毕业项目不该只是一个 CLI demo，也不该只是一个聊天界面。更硬的方向，是像 `RepoPilot Harness` 这样，把“自然语言需求 → 任务拆解 → agent 协作 → 隔离执行 → 验证交付”全都纳入一个产品化控制台里。
