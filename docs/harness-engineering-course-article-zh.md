# 真正的 Agent，难的不是模型，而是 Harness

副标题：学完这 12 节课，你会真正理解什么叫 Harness Engineering for Real Agents

> 如果你最近也在做 AI Agent，很容易先被模型吸引：用哪个模型、上下文多大、调用成本多少、推理强不强。
>
> 但当你真的开始把一个 Agent 做成“能长期运行、能真实做事、能持续交付”的系统时，你会很快发现：最难的部分，往往不是模型，而是模型外面那一整层 Harness。

这篇文章，想用一套非常落地的 12 节课程，把这件事讲清楚。

所谓 Harness，不是一个花哨的名词。你可以把它理解成：**围绕 LLM 搭建出来的一整套运行时系统**。它负责决定 Agent 怎么接任务、怎么思考、怎么调用工具、怎么切任务、怎么压缩上下文、怎么并行工作、怎么避免互相污染、怎么把结果真正落到文件和工程产物里。

也就是说：

- 模型决定 Agent “会不会思考”
- Harness 决定 Agent “能不能长期稳定地做事”

这也是为什么很多看起来很聪明的 Demo，一到真实场景就不行了。

不是因为模型太差，而是因为它没有运行时，没有任务系统，没有上下文治理，没有隔离机制，也没有协作协议。它只是“回答了一个问题”，并没有“完成一项工作”。

而这 12 节课的价值，就在于它不是教你做一个聊天机器人，而是一步一步带你搭出一个**真实 Agent Runtime**。

---

# 一、先讲结论：这 12 节课，本质上是在教你搭一台“本地 AI 工程协作台”

如果只看每节课标题，你可能会觉得它们有点散：

- Agent Loop
- Tool Use
- TodoWrite
- Subagent
- Skill Loading
- Context Compact
- Task System
- Background Tasks
- Agent Teams
- Team Protocols
- Autonomous Agents
- Worktree Isolation

但如果你把它们串起来看，就会发现它们其实是在完成同一件事：

**把一个自然语言需求，变成“任务拆解 -> 协作执行 -> 文件产出 -> 测试验证 -> 汇总交付”的完整流水线。**

这也是我们最后为什么会把毕业项目定义成 `RepoPilot Harness`。

因为这个项目最能体现 Harness Engineering 的核心能力：

- 有真实任务流转
- 有真实多 Agent 协作
- 有真实文件改动
- 有真实执行日志
- 有真实工作区隔离
- 有真实交付产物

它不是一个“会聊天的 AI”，而是一个“会组织开发工作的本地 Agent Runtime”。

# 二、这 12 节课，其实可以分成 3 个阶段来理解

## 阶段一：先让 Agent 活起来

前 4 节课解决的是最基础的问题：

**怎么让一个 Agent 不只是调一次模型，而是真的开始持续工作。**

### 第 1 课：Agent Loop

这是所有东西的起点。

很多人第一次做 Agent，本质上只是：

1. 用户输入一句话
2. 调一次模型
3. 输出一句回答
4. 结束

这不叫 Agent，这只是一次性推理。

真正的 Agent 至少要有 Loop，也就是：

- 读当前状态
- 决定下一步动作
- 执行动作
- 再看结果
- 继续下一轮
- 直到完成

一个最简单的例子是：

“帮我分析一个目录里有哪些 Python 文件，并统计总行数。”

如果没有 Loop，模型只能一次性猜。
如果有 Loop，它才能：

- 先看目录
- 再调用工具列文件
- 再读取文件
- 再统计
- 再汇总

从这节课开始，你第一次真正拥有了“会行动的 Agent”。

### 第 2 课：Tool Use

Agent 光会想还不够，它必须能碰到世界。

Tool Use 解决的是：**让模型不只输出文字，而是能调用外部能力。**

比如：

- 读写文件
- 列目录
- 执行命令
- 查询数据
- 发请求

举个最简单的例子：

“帮我读取 `README.md`，然后生成中文版摘要。”

这里就至少需要两个能力：

- 文件读取
- 文本生成

Tool Use 把“模型”和“环境”接起来，Agent 才第一次开始具备行动能力。

### 第 3 课：TodoWrite

很多人做 Agent 时，容易忽略一个非常关键的问题：

**任务状态怎么显式化？**

TodoWrite 的本质，不是做一个待办清单 UI，而是给 Agent 一个可外显、可追踪、可恢复的任务结构。

比如一个需求：

“帮我给项目加一个登录页，并补 README。”

如果没有 TodoWrite，模型往往会在上下文里“隐式记住”这两个任务。
但上下文一长，它就会忘，或者顺序混乱。

有了 TodoWrite，Agent 可以把它写成：

- [in_progress] 设计登录页结构
- [pending] 实现表单与样式
- [pending] 更新 README 使用说明
- [pending] 自测并汇总结果

这节课教会你的，是如何把 Agent 的思考过程从“脑内短记忆”变成“外部任务板”。

### 第 4 课：Subagent

当任务开始复杂，单 Agent 很快就会顶不住。

比如：

“帮我做一个小应用：前端页面、后端 API、README 一起完成。”

如果还是让一个 Agent 全包，它很容易：

- 上下文塞爆
- 关注点混乱
- 改动互相覆盖
- 任务优先级失控

Subagent 的意义在于：**把复杂任务拆成多个有边界的小执行单元。**

例如：

- 主 Agent：负责任务拆解与调度
- 子 Agent A：负责前端页面
- 子 Agent B：负责后端接口
- 子 Agent C：负责文档与测试说明

这节课开始，你第一次进入“多 Agent 世界”。

---

## 阶段二：让 Agent 能稳定跑很久

如果说前 4 节课是“让 Agent 活起来”，那中间 4 节课就是在解决另一个更难的问题：

**怎么让它活得久，而且活得稳。**

### 第 5 课：Skill Loading

真实 Agent 不可能把所有能力都硬编码在主程序里。

它需要一种“按需加载能力”的机制。

Skill Loading 解决的是：

- 不同任务如何挂载不同技能
- 能力如何模块化组织
- Prompt、工具、规则如何打包复用

举个例子：

同样是“写内容”，你可能需要不同 skill：

- 技术文档 skill
- SEO 写作 skill
- 数据分析 skill
- Git 操作 skill

Skill 的本质是：把“经验”沉淀成可复用的能力包，而不是每次都临时拼 Prompt。

这节课让你的 Agent 开始从“裸模型”升级成“带工具箱的工人”。

### 第 6 课：Context Compact

这是所有长任务系统都会遇到的生死问题。

上下文会无限膨胀。

只要任务一长，Agent 就会不断积累：

- 用户输入
- 中间日志
- 工具调用结果
- 文件内容
- 计划更新
- 子任务状态

如果没有 Context Compact，结果通常只有三个：

- 成本越来越高
- 速度越来越慢
- 记忆越来越乱

所以这节课讲的，不是简单摘要，而是：

**如何保留关键状态，丢弃低价值细节，让 Agent 继续跑下去。**

比如：

- 保留当前目标
- 保留任务板状态
- 保留关键文件结论
- 压缩长日志与历史思考

一个简单类比是：

人做项目时，也不会把每一分钟的聊天记录都背在脑子里，而是会保留“当前阶段最重要的信息”。

Context Compact，就是 Agent 的“阶段性记忆压缩机制”。

### 第 7 课：Task System

到了这里，Agent 已经不只是“会做事”，而是要开始“像系统一样管理工作”。

Task System 解决的是：

- 怎么创建任务
- 怎么查看任务
- 怎么更新任务状态
- 怎么记录事件流转
- 怎么让任务可以回放

一个现实例子：

“帮我做一个五子棋小游戏。”

在 Task System 里，它不会只是一个 Prompt，而会变成：

- 创建 Mission
- 自动拆成多个 Task
- 每个 Task 有状态变更
- 每次执行都有事件日志
- 最终汇总成产物与结果

这就是为什么任务板对真实 Harness 非常重要。

没有任务系统，Agent 做过什么很快就不可见；
有了任务系统，你才能真正看到“工作流在推进”。

### 第 8 课：Background Tasks

很多任务会卡主流程，比如：

- 长时间测试
- 构建打包
- 依赖安装
- 代码生成
- 异步轮询

如果主 Agent 一直阻塞等结果，它的吞吐就很差。

Background Tasks 的核心就是：

**把耗时动作放到后台执行，让前台调度继续推进。**

例如：

- Agent 启动一个测试任务
- 测试在后台跑
- 主流程继续处理别的任务
- 测试完成后，再把结果汇报回来

这节课真正教你的，是如何构建一个“不会因为长命令而卡死”的运行时。

## 阶段三：让 Agent 真正进入工程场景

最后 4 节课，才是很多人真正意识到“这不是 Demo，而是工程系统”的地方。

### 第 9 课：Agent Teams

Subagent 只是“分出去做”，Agent Teams 则是“组织协作”。

团队不是几个 Agent 名字摆在一起，而是：

- 有角色分工
- 有负责人
- 有协同节奏
- 有交付接口

一个很实际的案例是：

“做一个 MBTI 性格分析应用。”

你完全可以设计一个 3 人团队：

- Product Agent：拆需求、定义页面与功能边界
- Frontend Agent：实现输入表单、结果页和交互
- Content Agent：撰写 MBTI 类型说明与分析文案
- QA/Integrator Agent：联调、检查、汇总交付

这时候 Agent 已经不再是单兵，而开始像一个小型交付团队。

### 第 10 课：Team Protocols

团队一多，不制定协议一定会乱。

Team Protocols 解决的是：

- 任务如何交接
- 信息如何同步
- 结果如何汇报
- 冲突如何处理
- 文件所有权如何划分

为什么这节课特别重要？

因为没有协议，多 Agent 系统经常会出现这些问题：

- 两个 Agent 改同一个文件
- 一个 Agent 以为另一个做完了，其实没有
- 汇报格式五花八门，主 Agent 很难整合
- 任务边界模糊，反复返工

协议的作用，就是让协作从“混乱对话”变成“标准化交付”。

你可以把它理解成：给 AI 团队建立项目管理规则。

### 第 11 课：Autonomous Agents

前面很多课，主 Agent 还是偏强控制。

到了 Autonomous Agents，你开始让 Agent 具备更强的自驱能力：

- 自己发现下一步
- 自己判断是否完成
- 自己决定是否继续探索
- 自己触发更多动作

比如：

“请你阅读这个仓库，然后补齐缺失的文档，并做一次可运行性检查。”

这类任务无法完全提前写死。

Agent 需要一边探索，一边决策，一边推进。

这节课让你看到：

真正强大的 Agent，不只是执行固定流程，而是能在约束内自主行动。

但也正因为更自主，所以更需要 Harness 去兜底：

- 最大步数限制
- 任务边界
- 失败退出条件
- 状态记录
- 上下文压缩

越 Autonomous，越需要强 Runtime。

### 第 12 课：Worktree Isolation

这是毕业级的一课。

也是从“有点像 Agent”到“真的能进入工程生产场景”的分水岭。

多 Agent 同时改代码，最怕什么？

最怕互相污染。

比如：

- Agent A 改了前端
- Agent B 改了后端
- Agent C 改了 README
- 三个人都在同一个工作区改
- 最后改动冲突、状态混乱、难以回放

Worktree Isolation 解决的就是这个问题：

**给不同任务或不同 Agent 分配独立工作区，让它们在隔离环境里执行。**

这意味着：

- 每个任务有自己的代码空间
- 并行执行互不干扰
- 结果更容易审查
- 回滚与合并更可控

到了这里，你已经不是在写一个 Agent Demo，而是在搭建一个真正可运行的本地 AI 工程系统。

# 三、为什么很多 Agent 产品看起来聪明，但一做事就崩

学完这 12 节课，你会特别清楚一件事：

很多所谓 Agent 产品，不是真的不能做事，而是它们没有把“做事所需的运行机制”补全。

常见问题几乎都能在这套课程里找到对应答案：

## 1. 为什么它总是做着做着就忘了？

因为没有 TodoWrite，也没有 Context Compact。

它没有把任务结构外显，也没有把历史做阶段压缩。

## 2. 为什么它一复杂就乱？

因为没有 Subagent，也没有 Task System。

所有事情都挤在一个 Agent 上，它当然混乱。

## 3. 为什么它一跑长任务就卡死？

因为没有 Background Tasks。

所有事情都堵在主线程里，整个系统吞吐自然上不去。

## 4. 为什么多 Agent 协作像灾难现场？

因为没有 Team Protocols，也没有 Worktree Isolation。

没有协作规则，也没有执行隔离，出问题只是时间早晚。

## 5. 为什么它看起来很强，但总交付不了真实产物？

因为它本质上还是“对话系统”，不是“任务执行系统”。

它能回答问题，但不能组织工作。

而 Harness Engineering 的意义，就在这里：

**把 LLM 从“会说话”升级成“会交付”。**

# 四、如果把这 12 节课只记成一句话，我会这样概括

这 12 节课不是在教你“怎么调用一个模型”，而是在教你：

**怎么围绕模型，搭出一套真实可运行的 Agent Runtime。**

它解决的是从 Demo 到系统的跃迁：

- 从单轮回答，到持续循环
- 从文字生成，到工具执行
- 从脑内记忆，到任务板管理
- 从单兵作战，到多 Agent 协作
- 从同步阻塞，到后台任务
- 从短上下文，到长时运行
- 从共享目录乱改，到独立工作区隔离

这才是 Real Agents 真正的门槛所在。

# 五、毕业项目为什么一定是 RepoPilot Harness

如果要基于这 12 节课做一个毕业项目，我仍然最推荐 `RepoPilot Harness`。

因为它几乎把所有关键能力都串起来了。

它的目标不是回答问题，而是把一个自然语言开发需求，变成完整的软件交付流程：

1. 用户输入 Mission
2. 系统拆解任务
3. 分配给不同 Agent / Team
4. 在独立工作区里执行代码修改
5. 运行测试、检查结果
6. 汇总产物、日志与交付说明

它要解决的是非常真实的工程痛点：

- 单 Agent 写代码时，上下文容易乱
- 多任务并行时，文件改动会互相污染
- 长命令会阻塞主流程
- 多 Agent 没协议，很快失控
- 没任务板和事件记录，就无法回放过程

所以这个毕业项目的本质，不是做一个“AI IDE 插件”，也不是做一个“聊天机器人 UI”。

它是在做：

**一个本地 AI 工程协作台。**

当你真的把这个项目做出来，你会非常明显地感受到：

自己学到的已经不只是 Prompt Engineering，而是 Runtime、Workflow、Context Governance、Task Orchestration、Execution Isolation 这一整套系统能力。

# 六、给准备学这门课的人一个建议

如果你准备学这 12 节课，我建议不要把它当成“12 个零散例子”。

更好的方式是：

- 每学一课，就问自己它解决了什么真实运行问题
- 每学一课，就把它接回毕业项目里
- 每学一课，就做一次实际测试，记录结果
- 最后把它们串成一个完整 Runtime

这样你得到的就不只是知识点，而是一套真正能落地的工程方法。

你会开始明白：

- 为什么真实 Agent 不是一个 Prompt
- 为什么多 Agent 不是多开几个对话框
- 为什么上下文治理是核心工程问题
- 为什么任务系统决定可观察性
- 为什么隔离机制决定系统能不能真正上线

# 七、最后总结

如果用一句最直接的话来总结这门课，我会说：

**它教你的不是“怎么让 AI 更像人”，而是“怎么让 AI 真正像一个能工作的系统”。**

这正是 Harness Engineering 最迷人的地方。

它不只是研究“模型怎么回答”，而是在设计：

- Agent 怎么运行
- Agent 怎么协作
- Agent 怎么记住事情
- Agent 怎么调用环境
- Agent 怎么避免失控
- Agent 怎么真正把任务做完

而当这 12 节课学完，你获得的也不只是一个课程结论，而是一种新的工程视角：

**以后你看到任何一个 Agent 产品，都会下意识去问：它背后的 Harness 是怎么设计的？**

当你能开始问这个问题时，你其实已经从“Agent 的使用者”，走向“Agent Runtime 的构建者”了。
